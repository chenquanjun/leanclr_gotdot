# 11 CI 与依赖复现

本仓库的 CI 目标是「云端能跑出与本机相同的构建和 headless 回归结果」，不追求在 CI 里做设备测试。涉及五个工作流，用 `workflow_run` 串成一条链（见 §2.1）：

| 文件 | 触发 | 做什么 | 不做什么 |
|---|---|---|---|
| `.github/workflows/ci.yml` | push / PR / 手动 | 第 1 段：Windows 构建 GDExtension，跑 `hotreload` 与代码包 CLI 回归（56 + 70 项断言） | 不跑 MCP 通道、不导出 APK |
| `.github/workflows/linux.yml` | 第 1 段成功后 / 手动 | 第 2 段：Linux 构建 `.so`，跑同一组 CLI 回归 | 不跑 MCP 通道 |
| `.github/workflows/macos.yml` | 第 2 段成功后 / 手动 | 第 3 段：macOS（arm64）构建 `.dylib`，跑同一组 CLI 回归 | 不导出 `.app`、不签名/公证 |
| `.github/workflows/ios.yml` | 第 3 段成功后 / 手动 | 第 4 段：macOS runner 上交叉编译 arm64 静态库 `lib*.a` 并上传产物 | 不导出 `.ipa`、不签名、无设备/模拟器测试 |
| `.github/workflows/android.yml` | 第 4 段成功后 / 手动 | 第 5 段：Linux runner 上 3 个 ABI 各一个 matrix job（`fail-fast: false`），各自交叉编译、导出并上传自己的 debug APK 与原生库；`summary` job 汇总校验三份 APK | 无设备，不安装、不运行、不断言业务输出 |

各平台当前验到哪一层：

| 平台 | 构建 | 导出 | 运行/回归 | 状态 |
|---|---|---|---|---|
| Windows x64 | 已验 | 已验 | 已验（56 + 70 项） | 完整 |
| Linux x86_64 | 已验（WSL，见 §4） | 已验（PCK） | 待 runner 首跑 | 构建/导出已验，运行以 CI 日志为准 |
| macOS arm64 | CI 构建 | 未验 | CI headless 回归 | 首次 runner 运行前视为未验证 |
| iOS arm64（静态库） | CI 构建 | 未验（需签名） | 不可能在 CI 验 | 只到「产物成功」 |
| Android（3 ABI 分片） | 已验（本机串行） | 已验（3 份 APK，CI 由 `summary` 汇总校验） | 无设备 | 见 `docs/09`；单 ABI 的 runner 耗时未实测，见 §4 |

设备侧（MuMu 12）的验证仍在本机进行，步骤与证据见 `docs/09`。

## 1. 依赖如何复现

`native/thirdparty` 是 git submodule，固定 commit 写在 `.gitmodules`：

- `native/thirdparty/leanclr` → `focus-creative-games/leanclr` @ `8e024dfe`（mono 分支）
- `native/thirdparty/godot-cpp` → `godotengine/godot-cpp` @ `27d9dd23`（4.5）

工作流用 `actions/checkout@v4` 的 `submodules: recursive` 检出。**submodule 只解决来源，不解决能力**：阶段 B/C 的热更钩子与 arm32 参数偏移修复都在 `patches/leanclr-runtime-hotreload.patch`，必须再执行 `scripts/ensure_deps.ps1`（内部先 `submodule update --init --recursive`，再幂等应用补丁，冲突直接失败）。构建脚本自己也会调用它，所以 CI 里即使漏掉显式一步也不会编出「没有 `reload_assembly` 符号」的库。

### 1.1 版本固化与漂移检测

`native/thirdparty` 的版本只由**父仓库索引里的 gitlink**决定：

- `.gitmodules` 不含任何 `branch =`（有则 `verify_submodules.ps1` 直接报错），因此 `git submodule update`（不带 `--remote`）只会检出入库 commit，上游再更新也不会改变本地结果。
- `scripts/verify_submodules.ps1` 逐项比对「submodule 工作区 HEAD」与「HEAD（未提交时退回暂存区）里的 gitlink」，不一致就列出两边 commit 并以非 0 退出；未初始化也会明确提示先跑 `ensure_deps.ps1`。
- 该脚本被 `ensure_deps.ps1` 自动调用，五个 workflow 的入口 job 也各有一步 `Verify submodule pins`；本地提交前跑一次即可拦住「顺手 `git submodule update --remote` 后一起提交」的事故。

BCL 不入库，CI 用 `scripts/bootstrap_bcl.ps1` 从 submodule 的 `src/libraries/mono-4.5` 生成 154 个 dll 到 `godot_project/bin/bcl`。

### 1.2 平台特性宏：leanclr 内置 zlib 的 `HAVE_UNISTD_H`

leanclr 不引入系统 zlib，而是把 `src/runtime/3rd/zlib/*.c` 直接 GLOB 进 `leanclr` 静态库。这套 zlib 的 `zconf.h` 用 `#if HAVE_UNISTD_H-0` 决定是否定义 `Z_HAVE_UNISTD_H`，进而决定 `gzguts.h` 是否包含 `<unistd.h>`；上游由 `./configure` 生成这个宏，**leanclr 自己的 CMakeLists 不定义它**。

- Windows：`gz*.c` 走 `<io.h>` 分支（`_lseeki64`/`_read`/`_write`），不需要 `unistd.h`，所以问题不暴露。
- Linux/macOS：`gzlib.c`/`gzread.c`/`gzwrite.c` 调用的 `lseek`/`read`/`write`/`close` 没有声明。GCC 11 只给 warning（旧脚本能编过），**GCC 14+ 默认 `-Werror=implicit-function-declaration`，直接编译失败**。
- 修法：根 `CMakeLists.txt` 在 `add_subdirectory(leanclr)` 之后补 `target_compile_definitions(leanclr PRIVATE HAVE_UNISTD_H=1)`（`if(UNIX)`）。属于构建系统缺失的特性宏配置，不改第三方源码，因此不需要新增 `patches/`，`ensure_deps` 与 CI 无需额外步骤。
- Android 脚本里的 `-DCMAKE_C_FLAGS="-include unistd.h"` 是同一问题更早的局部 workaround，保留不动；新平台的扩展都靠上面的 CMake 定义。


## 2. 链式编排与本地预演

### 2.1 五个 workflow 用 `workflow_run` 串成严格链

```text
push(main)/PR/手动
      │
      ▼
ci.yml (Windows)          name: CI
      │ success
      ▼
linux.yml                 name: Linux CI
      │ success
      ▼
macos.yml                 name: macOS CI
      │ success
      ▼
ios.yml                   name: iOS build
      │ success
      ▼
android.yml               name: Android build + export
```

顺序按「快 → 慢」：Windows 先给最快反馈，Linux 次之，macOS / iOS 是 macOS runner 上的长构建，Android 最后（3 个 ABI + 约 1GB 导出模板）。

| 段 | 文件 | `name:`（下游逐字引用） | 触发 |
|---|---|---|---|
| 1 | `ci.yml` | `CI` | `push` / `pull_request` / `workflow_dispatch` |
| 2 | `linux.yml` | `Linux CI` | `workflow_run: workflows: ["CI"]`, `types: [completed]` / `workflow_dispatch` |
| 3 | `macos.yml` | `macOS CI` | `workflow_run: ["Linux CI"]` / `workflow_dispatch` |
| 4 | `ios.yml` | `iOS build` | `workflow_run: ["macOS CI"]` / `workflow_dispatch` |
| 5 | `android.yml` | `Android build + export` | `workflow_run: ["iOS build"]` / `workflow_dispatch` |

**失败即停**：`workflow_run` 只表示「上游 run 完成了」，**不区分成败**，所以每个下游入口 job 都显式写了：

```yaml
if: github.event_name == 'workflow_dispatch' || github.event.workflow_run.conclusion == 'success'
```

上游是 `failure` / `cancelled` / `skipped` 时，下游整个 run 只有一个 skipped job（结论 `skipped`），再往下的段同样不满足 `success`，链就此停住。没有用 `if: always()` 去吞失败；日志上传步骤上的 `if: always()` 只负责在失败时把 `out/logs/` 传成 artifact。Android 的 `summary` job 也从 `if: always()` 改成 `needs.build-export.result == 'success'`，任一 ABI 失败就不会进入汇总，整个 run 保持 failed。

**手动补跑（从链中任意一段开始）**：五个文件都保留 `workflow_dispatch`；手动触发时 `github.event_name == 'workflow_dispatch'`，`||` 左侧为真，直接跳过上游 conclusion 判断，不受任何上游限制。例如只重跑 macOS：Actions → macOS CI → Run workflow；只验证 Android：Actions → Android build + export → Run workflow。手动跑下游不会回头补跑上游。

**检出的是哪个提交**：`workflow_run` 默认检出**默认分支 HEAD**，不是触发链的那个提交。因此下游 `actions/checkout` 一律写 `ref: ${{ github.event.workflow_run.head_sha || github.sha }}`，否则「push 之后又来一次 push」时会测到更新的代码。

### 2.2 `workflow_run` 的实际约束

| 约束 | 具体表现 | 对「push 到 main 自动串行」的影响 |
|---|---|---|
| 只在默认分支上的 workflow 定义生效 | 带 `workflow_run` 的 `linux.yml` 等必须先在 main 上存在，否则永远不触发 | 无影响；本次改动合入 main 后开始生效（首个 push 即可） |
| 只在默认分支上的 run 完成后触发 | feature 分支 push 与 PR 的 `ci.yml` run 完成后不会拉起 `linux.yml` | 无影响；目标就是 main 上的串行。非 main 分支与 PR 只跑第 1 段 Windows，需要全量验证时用 `workflow_dispatch` |
| fork PR 不触发 | 外部贡献的 PR 不进链 | 无影响；fork PR 至多跑第 1 段（PR 事件本身） |
| 拿不到上游 run 的完整上下文与产物 | 只有 `conclusion`、`head_sha`、`head_branch`、`id` 等元数据；上游 artifact 要用 REST API + `download-artifact` 捞 | 无影响；每段自建自测，不依赖上游产物 |

### 2.3 为什么不再保留 `concurrency: leanclr-ci`

链式下自动触发的 run 天然串行（下一段要等上一段 complete 才产生），而共享并发组反而有害：同组只保留 1 running + 1 pending，**下一段排队时会顶掉正在 pending 的 run**。例如连续两次 push 到 main：push#2 的 `ci.yml` 正在排队，push#1 的 `linux.yml` 一排队就会把 `ci.yml#2` 取消，push#2 的整条链直接消失。

因此现在五个文件都不设 `concurrency`：

- 自动链不会并发（`workflow_run` 保证先后）。
- 手动重复触发可能与自动链重叠，这正是排查时想要的（不同 runner 互不影响）。
- 如果以后想对「同一段的重复手动触发」去重，可加 `group: ${{ github.workflow }}`，只影响同一 workflow 的重复触发，不会误伤链上的其他段。

**代价**：首个反馈比并行慢。原来是「所有平台同时开跑，等最慢的那个」，现在是严格顺序，最慢的 Android 排最后，出全部结果的时间和 ≈ 各段之和。需要快速判断某平台是否坏掉时，直接用 `workflow_dispatch` 单跑那一段。

### 2.4 本地预演同样的步骤

#### Windows（对应 ci.yml 的 windows job）

```powershell
git submodule update --init --recursive
powershell -ExecutionPolicy Bypass -File scripts\verify_submodules.ps1
powershell -ExecutionPolicy Bypass -File scripts\ensure_deps.ps1
powershell -ExecutionPolicy Bypass -File scripts\bootstrap_bcl.ps1
scripts\build_native.bat
powershell -ExecutionPolicy Bypass -File scripts\hotreload.ps1 -Channel cli
powershell -ExecutionPolicy Bypass -File scripts\code_pkg_test.ps1 -Channel cli
```

Godot 路径的解析顺序是 `-GodotExe` > `GODOT_BIN` > `.tools/godot45/` 下的默认文件名；CI 固定下载到 `.tools/godot45/`，与脚本默认路径一致，本地无需额外参数。输出目录默认为仓库内 `out/`，可用 `LEANCLR_OUT` 改到别处。

#### Linux（对应 linux.yml）

```bash
git submodule update --init --recursive
pwsh ./scripts/ensure_deps.ps1
pwsh ./scripts/bootstrap_bcl.ps1
bash scripts/build_native_linux.sh
./.tools/godot45/Godot_v4.5-stable_linux.x86_64 --headless --path godot_project --import
pwsh ./scripts/hotreload.ps1 -Channel cli -GodotExe "$PWD/.tools/godot45/Godot_v4.5-stable_linux.x86_64"
pwsh ./scripts/code_pkg_test.ps1 -Channel cli -GodotExe "$PWD/.tools/godot45/Godot_v4.5-stable_linux.x86_64"
```

`-GodotExe` 是本轮为跨平台补的参数；不传时仍用 Windows 默认路径。两个测试脚本内部路径已改成 `Join-Path` 组合，Linux 下不会再生成带反斜杠的路径。

#### macOS（对应 macos.yml）

```bash
git submodule update --init --recursive
pwsh ./scripts/ensure_deps.ps1
pwsh ./scripts/bootstrap_bcl.ps1
bash scripts/build_native_macos.sh
"$PWD/.tools/godot45/Godot.app/Contents/MacOS/Godot" --headless --path godot_project --import
pwsh ./scripts/hotreload.ps1 -Channel cli -GodotExe "$PWD/.tools/godot45/Godot.app/Contents/MacOS/Godot"
pwsh ./scripts/code_pkg_test.ps1 -Channel cli -GodotExe "$PWD/.tools/godot45/Godot.app/Contents/MacOS/Godot"
```

`build_native_macos.sh` 默认按宿主架构（Apple Silicon 为 `arm64`）编译 `out/bin/macos/leanclr_godot.dylib` 并部署到 `godot_project/bin/`；需要通用包时 `LEANCLR_MACOS_ARCHS="arm64;x86_64"`。`.gdextension` 里对应 `macos.debug.arm64` / `macos.release.arm64`，未构建 `x86_64` 变体。

#### iOS（对应 ios.yml）

```bash
pwsh ./scripts/ensure_deps.ps1
bash scripts/build_native_ios.sh Debug      # 产物 out/bin/ios/libleanclr_godot.ios.debug.a
```

- iOS 的 GDExtension 是**静态库**：`CMakeLists.txt` 在 `CMAKE_SYSTEM_NAME=iOS` 时把 `leanclr_godot` 切成 `STATIC`（名字带 `lib` 前缀），并跳过 `leanclr_smoke` 可执行程序。
- 交叉编译用 CMake 原生 iOS 支持：`-DCMAKE_SYSTEM_NAME=iOS -DCMAKE_OSX_SYSROOT=iphoneos -DCMAKE_OSX_ARCHITECTURES=arm64 -DCMAKE_OSX_DEPLOYMENT_TARGET=12.0`；脚本额外 `export SDKROOT=<iphoneos sdk>`，因为 godot-cpp 的 `cmake/macos.cmake` 会用 `$ENV{SDKROOT}` 覆盖 `CMAKE_OSX_SYSROOT`。
- 产物是**自包含静态库**：`libtool -static` 把 `libleanclr_godot.a`、`libgodot-cpp.ios.template_*.arm64.a`、`libleanclr.a` 合并成一个 `.a`。Godot 的 iOS 导出只链接 `.gdextension` 里列的库，不会替我们链接第三方静态库；不合并会在 Xcode 链接阶段报大量未定义符号。
- 只覆盖真机 `arm64`；`iphonesimulator`、`x86_64` 未配置。产物部署到 `godot_project/bin/ios/`，`.gdextension` 用 `ios.debug` / `ios.release` 指向它。
- 导出 `.ipa` 不在 CI 内：那一步需要 macOS Godot 编辑器 + Xcode 工程 + Apple 开发者证书与 provisioning profile，属于本仓库未验证范围。

#### Android（对应 android.yml）

```bash
export ANDROID_HOME=/path/to/android-sdk
export ANDROID_NDK_HOME=$ANDROID_HOME/ndk/<ver>
bash scripts/build_android_linux.sh x86_64 Debug
bash scripts/build_android_linux.sh arm64-v8a Debug
bash scripts/build_android_linux.sh armeabi-v7a Debug
```

本地是三条命令串行；CI 里拆成三个独立 job（`x86_64` / `arm64-v8a` / `armeabi-v7a`，`fail-fast: false`），每个 job 只跑一条 `build_android_linux.sh <abi> Debug`、只导出自己那份 APK，workspace 互不共享。`summary` job 通过 `needs` 依赖三者，下载分片产物后断言三份 APK 都在。

导出 APK 需要导出模板（`Godot_v4.5-stable_export_templates.tpz`，约 1GB）与 debug keystore。入库的 `export_presets.cfg` 里 `keystore/debug` 是**空字符串**（不绑定本机路径），Godot 不会展开 `~`/环境变量，所以导出前必须注入绝对路径：

- 本地：`code_pkg_android_test.ps1` / `code_pkg_switch.ps1` 通过 `scripts/lib/repo.ps1` 的 `Invoke-WithDebugKeystore` 解析 `ANDROID_DEBUG_KEYSTORE` > `~/.android/debug.keystore`，临时写入预设、导出后还原。
- CI：每个 ABI job 各生成一次 `~/.android/debug.keystore`（`keytool`，已存在则跳过），再用 `sed` 把预设的该行替换为 runner 路径（只改工作区副本，不提交）。

## 3. 缓存与产物

- `out/build` 用 `actions/cache` 缓存，key 包含 `CMakeLists.txt`、`patches/*.patch`、`native/src/**`、`.gitmodules` 的哈希；恢复旧缓存只会触发增量重编，不会改变结果。macOS / iOS 的 key 额外带 `runner.os` 与 `runner.arch`，避免与 Linux 的缓存混用（iOS job 用 `ios-native` 前缀单独隔离）。Android 的 key 再带 `matrix.abi`（`android-native-<abi>-<hash>`），三个 ABI 的构建目录互不覆盖。
- thirdparty 源码不单独缓存：submodule 固定 commit，`actions/checkout` 的 `submodules: recursive` 直接拉取即可；若之后 clone 变慢，可在工作流里加 `.git/modules` 缓存，但不要缓存工作区文件（补丁应用状态会不一致）。
- Android 的三个 ABI job 共享三份与 ABI 无关的缓存：`.tools/godot45`（Godot 4.5 Linux 二进制）、`~/.local/share/godot/export_templates/4.5.stable`（导出模板，约 1GB）、`godot_project/bin/bcl`（154 个 dll，key 用 mono-4.5 顶层 dll 与 `Facades/netstandard.dll` 的哈希）。首次 run 三个 job 同时未命中会各自下载/生成，后到的保存会因 key 已存在而跳过（只打 warning），从第二次 run 起命中。
- 日志统一写 `out/logs/`，`if: always()` 上传为 `windows-logs` / `linux-logs` / `macos-logs` / `ios-logs` / `android-logs-<abi>`；Android 每个 ABI 另传 `android-apk-<abi>`（该 ABI 的 APK + `out/bin/android/<abi>/`），最后由 `summary` 的 `android-artifacts` 合并三份 APK。失败时直接看 artifact 里的 `godot_hotreload_c.log`、`godot_code_pkg_test.log`、`android_native_<abi>_debug.log`。iOS job 还额外上传 `ios-static-lib`（`out/bin/ios/*.a`，缺失时该步骤失败）。
- 产物：Android `out/android/*.apk`、`out/bin/android/<abi>/`；macOS `out/bin/macos/leanclr_godot.dylib`；iOS `out/bin/ios/libleanclr_godot.ios.<debug|release>.a`。

## 4. 已知限制

- **MCP 通道不进 CI**：`scripts/mcp_run_scene.mjs` 依赖本地构建的 godot-mcp（`.tools/godot-mcp`，未入库）。CI 只跑 CLI 通道；MCP 断言需在开发机执行。
- **Android 无设备**：工作流只证明「能编译、能导出 APK」。安装、转译层、业务输出断言不在 CI 里，见 `docs/09` 的 MuMu 实测记录。
- **macOS 只验到构建 + headless 回归**：`macos.yml` 在 `macos-latest`（arm64）上编译 `template_debug` 的 `.dylib`，用 `file`/`otool -L`/`nm` 检查架构、依赖与 `leanclr_godot_init` 符号，再跑与 Windows/Linux 相同的 CLI 回归。**不导出 `.app`**（需要导出模板、`export_presets.cfg` 的 macOS 预设与签名）；`x86_64` 与 universal 未构建；签名/公证未验证。首次 runner 运行前，这一层仍视为未验证。
- **iOS 只验到静态库产物**：`ios.yml` 在 macOS runner 上交叉编译 arm64 静态库，检查 `lipo -info` 与入口符号后上传 artifact。**不做 `.ipa` 导出、不做签名、没有设备/模拟器测试**；`ios.debug`/`ios.release` 的 `.gdextension` 条目尚未经过真实导出验证（Godot 4.5 iOS 导出的 Xcode 工程链接行为、最小 iOS 版本、Bitcode 策略都属未验证范围）。
- **Linux 构建已在本机 WSL 验证，Godot headless 断言未在 runner 上实跑**：WSL Ubuntu 22.04（gcc/g++ 11.4 / CMake 3.22）执行同一份 `scripts/build_native_linux.sh`，产物 `out/bin/linux/leanclr_godot.so`（2,904,064 字节）已部署到 `godot_project/bin`；`ldd -r` 无缺失依赖、无未解析符号，`readelf -d` 的 `NEEDED` 只有 libstdc++/libm/libgcc_s/libc 与 ld-linux（无额外运行时依赖），导出符号含 `leanclr_godot_init`，日志在 `out/logs/ci_linux_build.log`。另用 `leanclr_smoke`（不依赖 Godot 的纯 leanclr 冒烟程序）验证解释器链路：第一轮输出 `test.App::Run(1, 2) = 3`、`test.App::Test1() = Hello, World!`、中文字符串与日志回调正常；第二轮 `Runtime::initialize`（shutdown 后重新初始化）报错 26，**该失败在 Windows 上的同一份 `leanclr_smoke.exe` 完全一致，属既有问题，与本次 zlib/平台改动无关**，日志在 `out/logs/ci_linux_smoke_run.log`。
- zlib 复现/修复的对照日志在 `out/logs/ci_linux_zlib_repro.log`：不定义宏时三条 `.c` 各自报 `implicit declaration of function 'lseek'/'read'/'write'/'close'`（与本机 gcc 11 加 `-Werror=implicit-function-declaration`，等价于 CI 的 GCC 14 默认行为），加上 `-DHAVE_UNISTD_H=1` 后三条全部 `compile_exit=0`。
- 本机 WSL 没有 PowerShell 7/.NET，且 Godot Linux 二进制下载带宽只有约 16 KB/s（65.8MB 预计 70 分钟，已中止），因此「Godot headless + CLI 回归」这一步仍留给 CI；若首跑失败，日志会给出具体缺失项，按日志补步骤，不要放宽断言。当前 Linux 侧的结论是：**编译、链接、`ldd`、`.so` 产物、leanclr 解释器运行均已验证；Godot 集成运行未在本机验证**。
- **Android 导出步骤未实跑**：`--export-debug` 需要 Android SDK 的 `apksigner`/`zipalign` 与编辑器设置里的 SDK 路径；工作流已写入 `export/android/android_sdk_path`，但 runner 镜像差异可能导致首次运行失败。失败时 artifact 里有完整导出日志。
- **单 ABI 的 runner 耗时未实测**：之前是一个 job 串行编译三个 ABI，撞上 `timeout-minutes: 120` 被取消；现在每个 ABI 一个 job，各 `timeout-minutes: 90`。本机没有 Android SDK/NDK、Godot 二进制下载带宽也只有约 16 KB/s，无法测出单个 ABI 的真实耗时，所以「单 ABI 能在 90 分钟内完成」目前只是按「总时长的一半以下」推断，属未验证。首次 runner 运行后按 `android_native_<abi>_debug.log` 里的 configure/build 时间段核对；若仍接近上限，先确认缓存是否命中（Godot 二进制、导出模板、BCL 都应命中），再考虑缩小编译并行度而不是放宽超时。
- **链式行为需 push 后首跑才能确认**：`workflow_run.workflows` 的名字与各 `name:` 已做逐字静态校验（大小写、空格），链条顺序也核对为 CI → Linux CI → macOS CI → iOS build → Android build + export；但「上游 failure → 下游整 run skipped → 再下游不触发」的传播、`head_sha` 是否检出正确提交、默认分支限制，只能在真实 runner 上看到。首跑时若某一环没出现，先确认上一段结论是 `success`、再看 `workflow_run.workflows` 的字符串是否与上游 `name:` 完全一致（这是链式最常见的错法）。
- **首个反馈变慢**：并行时所有平台同时开跑，只等最慢的一个；现在严格按顺序，Android 排最后，拿到全部结果的时间约等于各段之和。需要快速定位某个平台时用 `workflow_dispatch` 单跑那一段（见 §2.1）。
- **导出模板体积**：`Godot_v4.5-stable_export_templates.tpz` 约 1GB，所以 Android 排在第 5 段（只在前面全部通过后才下载）；模板已纳入 `actions/cache`，首次 run 三个 ABI job 会各自下载一次，之后命中缓存。
- **本机没有 `act` / `actionlint`**：工作流只做了静态核对——PyYAML 解析 5 个 workflow（含链名逐字比对）、从 workflow 中抽出全部 bash 步骤做 `bash -n`、PowerShell `Parser::ParseFile` 检查全部 `.ps1`、命令与产物路径逐条对照脚本源码；GitHub runner 上的实际执行结果以首次运行的日志为准。

### 4.1 Windows 首次导入（无 `.godot`）在退出阶段 signal 11

**现象**：干净 checkout（没有 `godot_project/.godot`）执行 `--import` 时，进程以 `-1073741819`（`0xC0000005` access violation，Godot 打印 `Program crashed with signal 11`）退出，崩溃栈只有一串 `no debug info in PE/COFF executable`（官方版 Godot 没有 PDB，dbghelp 解析不到帧）。Windows job 首跑就卡在这一步。

**已确认的事实**（在全新目录按 `ci.yml` 顺序复刻：`verify_submodules` → `ensure_deps` → `bootstrap_bcl` → `build_native.bat` → `--import`）：

| 条件 | 结果 |
| --- | --- |
| 有 `.godot` + 扩展启用 | exit 0 |
| 删掉 `.godot` + 扩展启用 | exit `-1073741819`（必现） |
| 删掉 `.godot` + 禁用 `.gdextension` | exit 0 |
| 删掉 `.godot` + 全新 `APPDATA`/`LOCALAPPDATA` | exit `-1073741819`（同一现象，用户 profile 不是变量） |

- 崩溃在**编辑器退出阶段**：日志最后是 `first_scan_filesystem [ DONE ]`、`update_scripts_classes [ DONE ]`、`loading_editor_layout [ DONE ]`、`Loading resource: res://demo.tscn|demo.gd`、`EditorSettings: Save OK!`，之后才 signal 11。导入本身已经完成。
- 崩溃时 `.godot/extension_list.cfg` **已写好**（内容 `res://bin/leanclr_godot.gdextension`），**紧接着复跑同一条 `--import` 命令 exit 0**，之后的 CLI 回归 56/56、70/70 全通过。
- 这与 `docs/04` §1、`docs/07` §1 记录的「编辑器 headless 首次导入可能以 signal 11 结束，只要生成了 `extension_list.cfg` 即可继续」一致，属**既有现象**：本轮没有改 `native/src`，只改了 macOS/iOS 工作流、`if(UNIX)` 的 `HAVE_UNISTD_H` 与链式编排，与该崩溃无因果关系。
- 崩溃模块：Windows 事件日志（`Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000}`）里的历史记录给出 `出错模块名称：leanclr_godot.dll`、`异常代码 0xc0000005`，即 AV 落在扩展内部，而不是 Godot 或 BCL 缺失。

**为什么本地一直没暴露**：本机每次改完都会先导入过一次，`godot_project/.godot` 一直存在，`--import` 走的是「有缓存」分支，exit 0；`hotreload.ps1` / `code_pkg_test.ps1`（56/56、70/70）只跑场景、不重建缓存。「本地全绿」只覆盖了有缓存的分支，不覆盖首次导入。

**尝试过但拿不到可读栈的方式**（记录于此避免重复投入）：

- 给扩展加 `/Zi` + `/DEBUG` 并把 PDB 随 DLL 部署后，Godot 崩溃处理器**仍然**只输出 `no debug info in PE/COFF executable`（它没有加载我们模块的 PDB），栈依旧不可读，故这一改动没有入库。
- 用 `DEBUG_PROCESS` 跟随 console 启动器抓 AV：**崩溃不复现**（时序敏感），拿不到异常地址。注意 `Godot_v4.5-stable_win64_console.exe` 只有 197KB，是启动器，真正引擎是同级 `Godot_v4.5-stable_win64.exe`。
- WER 本地转储不可用：本机 `WerSvc` 处于 Stopped，`LocalDumps` 注册表不生效；且 Godot 自带崩溃处理器会先接管异常。

**CI 的判定方式**（`.github/workflows/ci.yml` 的 `Import Godot project`）：不以首次退出码判失败，而是

1. 断言 `.godot/extension_list.cfg` 存在且登记了 `leanclr_godot.gdextension`；
2. 首次 exit ≠ 0 时复跑一次 `--import`，要求第二次 exit 0（证明缓存可被后续 CLI 回归复用）；两次都失败才让 job 失败。

日志：首次 `out/logs/godot_import.log`、复跑 `out/logs/godot_import_second.log`，随 `windows-logs` 上传；失败时另有 `windows-import-diagnostics`（含 `godot_project/.godot/`），用于区分「导入中途崩溃」与「退出阶段崩溃」。

**规避与后续**：本地复现首次导入路径就删掉 `.godot`，接受一次 signal 11 后复跑一次即可；不要因为它把 `--import` 整体判红，也不要用「跳过导入」来绕过（那会同时跳过扩展登记校验）。该 signal 11 的**具体函数仍未定位**：若要继续，需要在 runner 或本机安装 Debugging Tools for Windows，用 `cdb -g -G` 跑首次导入，或自编译带符号的 `target=editor` Godot；这属于一次性投入，暂不纳入 CI。

## 5. 升级依赖或补丁

**不要用 `git submodule update --remote`**：它会让工作区 HEAD 离开入库 gitlink，`verify_submodules.ps1` 会报错。有意升级按下面顺序做，并一次性提交：

```powershell
# 1) 切 submodule 到目标 commit（显式指定，不跟随分支）
git -C native/thirdparty/leanclr fetch origin mono
git -C native/thirdparty/leanclr checkout <new-commit>
git add native/thirdparty/leanclr

# 2) 重新应用/重生成补丁（冲突会明确报错）
powershell -ExecutionPolicy Bypass -File scripts\apply_patches.ps1

# 3) 更新固化校验与文档里的 commit 记录
powershell -ExecutionPolicy Bypass -File scripts\verify_submodules.ps1
#    docs/11 §1 的 commit 表、AGENTS.md §1 同步为新 commit
```

冲突时在 submodule 内手工 `git apply --3way patches/leanclr-runtime-hotreload.patch`，解决后重新生成补丁：

```powershell
git -C native/thirdparty/leanclr add -A src/runtime
git -C native/thirdparty/leanclr diff --cached --binary --output=patches/leanclr-runtime-hotreload.patch
git -C native/thirdparty/leanclr reset
```

godot-cpp 若有本地改动，按同样方式生成 `patches/godot-cpp-*.patch`（当前无改动，`git -C native/thirdparty/godot-cpp status` 为空）。
